# Security — AMB Personal Portfolio

وضعیت: پیش‌نویس Phase 0 | نسخه: 0.1
این سند الزامات امنیتی، مدل تهدید و چک‌لیست پیش از استقرار را تعیین می‌کند. قابلیتی که امنیت آن تأیید نشده، «آماده تحویل» اعلام نمی‌شود.

## 1. مدل تهدید (خلاصه)

| دارایی | تهدید اصلی | کنترل اصلی |
|---|---|---|
| حساب مدیر | حدس رمز، سرقت نشست | محدودیت ورود، رمز قوی، نشست امن، (اختیاری) 2FA، Audit |
| پنل مدیریت | دسترسی غیرمجاز، CSRF، XSS | Policy، CSRF، CSP، Sanitizer |
| فرم‌های عمومی | اسپم، ثبت تکراری، سوءاستفاده از پیامک/ایمیل | Honeypot، زمان‌سنج، Rate Limit، Idempotency، سقف روزانه |
| آپلود فایل | اجرای کد، فایل مخرب، Path Traversal | اعتبارسنجی MIME/پسوند، Re-encode، ذخیره امن |
| محتوای TipTap | XSS ذخیره‌شده | Sanitizer سمت سرور با Allowlist |
| Installer/Updater وب | اجرای غیرمجاز migration یا نصب مجدد | توکن، قفل، IP/Rate limit، غیرفعال‌سازی |
| فایل‌های حساس | افشای `.env`، سورس، لاگ | خارج از Document Root، `.htaccess`، مجوزها |
| اطلاعات مشتریان | افشای PII | کمینه‌سازی، دسترسی نقش‌محور، Retention، لاگ بدون PII |
| وابستگی‌ها | آسیب‌پذیری زنجیره تأمین | Audit در Build، قفل نسخه، بازبینی |

## 2. احراز هویت و نشست

- Laravel auth با Hash استاندارد (Bcrypt/Argon2 طبق پیش‌فرض Laravel).
- سیاست رمز: حداقل 12 نویسه برای مدیر، بررسی رمزهای رایج/افشاشده در حد معقول، بدون الزام ترکیب‌های ناخوشایند.
- ورود: Rate Limit مبتنی بر `(email + IP)` و جداگانه IP؛ قفل موقت پیشرونده؛ پیام خطای یکسان (بدون افشای وجود حساب).
- بازیابی رمز: توکن یکبارمصرف و کوتاه‌عمر، Rate Limit، پیام یکسان.
- نشست: `session.secure`, `http_only`, `same_site=lax`، بازتولید ID پس از ورود/تغییر سطح دسترسی، انقضای معقول، خروج امن (ابطال نشست).
- نشست پنل و حساب مشتری از هم تفکیک‌پذیر (Guard/نقش جدا یا حداقل نقش جدا).
- تغییر رمز/ایمیل: نیاز به رمز فعلی؛ ابطال نشست‌های دیگر.
- 2FA (TOTP) برای مدیر: توصیه می‌شود؛ پیاده‌سازی پس از ارزیابی وابستگی (در Phase 3 تصمیم‌گیری و در ADR ثبت شود).
- هیچ حساب پیش‌فرض یا رمز ثابت در Seeder تولیدی؛ حساب مدیر اولیه فقط از Installer با رمز انتخابی.

## 3. کنترل دسترسی

- `spatie/laravel-permission` برای نقش/مجوز؛ Policy برای هر مدل؛ بررسی در Controller و (برای داده) در Query.
- مخفی‌کردن دکمه در UI کنترل دسترسی نیست؛ هر مسیر Admin با Middleware `auth` + `can`.
- هر Policy با تست برای هر نقش (مدیر، ویراستار، مشتری، مهمان) پوشش داده می‌شود.
- مشتری فقط به داده خودش دسترسی دارد (Scope سراسری + Policy)؛ تست نفوذ سطح شیء (IDOR) برای هر مسیر مشتری.
- شناسه‌های عمومی (درخواست، رزرو) ULID یا کد پیگیری غیرقابل حدس، نه شناسه عددی ترتیبی.
- مسیر Installer و Updater فقط با توکن + نقش Admin؛ پس از نصب قفل و (ترجیحاً) حذف/غیرفعال.

## 4. ورودی و خروجی

- اعتبارسنجی سمت سرور برای همه ورودی‌ها (Form Request)؛ اعتبار سمت کلاینت فقط کمکی.
- نرمال‌سازی متن فارسی قبل از اعتبارسنجی.
- XSS: خروجی Blade به‌صورت پیش‌فرض Escape می‌شود؛ `{!! !!}` فقط برای HTML پاک‌سازی‌شده و در نقاط ثبت‌شده.
- TipTap: HTML ورودی با Allowlist تگ/ویژگی/پروتکل پاک‌سازی می‌شود (Sanitizer سمت سرور؛ انتخاب کتابخانه با ADR)؛ `javascript:` و `data:` غیرمجاز؛ `rel="noopener noreferrer"` برای لینک‌های خارجی.
- SQL Injection: فقط Eloquent/Query Builder با Binding؛ Raw فقط با پارامتر و بازبینی.
- Mass Assignment: `$fillable` صریح.
- Header Injection (ایمیل): اعتبار `email`، حذف CR/LF از فیلدهای Header.
- Open Redirect: پارامترهای بازگشت فقط به مسیرهای داخلی Allowlist؛ جدول `redirects` فقط توسط مدیر و با اعتبارسنجی مقصد.
- URL خارجی (لینک پروژه/مخزن): فقط `http/https`، بدون اتصال سمت سرور به URL دلخواه کاربر (جلوگیری از SSRF). دریافت GitHub فقط از میزبان ثابت و Allowlist.

## 5. آپلود فایل

- Allowlist نوع: تصویر (JPEG, PNG, WebP, AVIF در صورت پشتیبانی)، PDF (برای رزومه/مدرک، فقط مدیر). SVG آپلودی فقط توسط مدیر و پس از Sanitize یا ممنوع (تصمیم در Phase 3؛ پیش‌فرض: ممنوع).
- بررسی MIME واقعی با `finfo` (نه فقط پسوند/Content-Type کلاینت)، پسوند Allowlist، سقف حجم، سقف ابعاد تصویر.
- تصاویر با GD/Imagick دوباره کدگذاری می‌شوند (حذف EXIF/payload).
- نام فایل ذخیره‌شده تصادفی (ULID/hash)؛ نام اصلی فقط به‌عنوان متادیتا و Escape شده.
- مسیر ذخیره: `storage/app/public` با لینک یا مسیر خارج از ریشه؛ هرگز اجرای PHP در مسیر آپلود (`.htaccess` با `php_flag engine off` یا معادل / `Options -ExecCGI` و رد `*.php`).
- جلوگیری از Path Traversal: مسیرها از ID/نام تولیدشده ساخته می‌شوند، نه ورودی کاربر.
- فایل خصوصی (مدارک، رزومه خام): دسترسی از طریق Controller و Policy، نه URL مستقیم.

## 6. فرم‌های عمومی و ضد سوءاستفاده

| لایه | رفتار |
|---|---|
| Honeypot | فیلد نامرئی (برای صفحه‌خوان مخفی)؛ پر شدن = رد بی‌صدا + لاگ |
| زمان‌سنج | حداقل زمان تکمیل فرم؛ توکن امضاشده با زمان |
| Rate Limit | به‌ازای IP و (در صورت وجود) ایمیل/تلفن؛ سقف روزانه و دقیقه‌ای |
| Idempotency | کلید یکتا برای جلوگیری از ثبت تکراری (دوبار کلیک/Refresh) |
| CAPTCHA | پیش‌فرض خاموش؛ اگر لازم شد، راهکار سازگار با ایران (مثلاً CAPTCHA خودمیزبان) و بدون وابستگی به سرویس مسدودشده؛ تصمیم با ADR |
| سقف پیامک | سقف روزانه کل و به‌ازای شماره/IP تا هزینه و سوءاستفاده کنترل شود |
| اعلان‌ها | محتوای کاربر در ایمیل/پیامک Escape/کوتاه شود؛ بدون لینک دلخواه |

Rate Limitهای پیشنهادی اولیه (قابل تنظیم از Config، در Phase 3 نهایی می‌شوند): ورود 5 تلاش در دقیقه به‌ازای (email+IP)؛ بازیابی رمز 3 در ساعت؛ فرم تماس 5 در ساعت به‌ازای IP؛ درخواست همکاری 3 در ساعت به‌ازای IP؛ رزرو 5 در ساعت؛ تخمین هزینه 30 در ساعت؛ Installer 10 در ساعت.

## 7. هدرها و CSP

- `Strict-Transport-Security` (پس از تأیید HTTPS و SSL پایدار؛ شروع با `max-age` کوتاه).
- `X-Content-Type-Options: nosniff`، `Referrer-Policy: strict-origin-when-cross-origin`، `Permissions-Policy` محدود، `X-Frame-Options`/`frame-ancestors 'self'`.
- CSP: چون همه Asset ها محلی‌اند، CSP سخت‌گیرانه ممکن است: `default-src 'self'`، `script-src 'self'` + Nonce/Hash برای اسکریپت inline تم، `style-src 'self'`، `img-src 'self' data:`، `font-src 'self'`، `connect-src 'self'`، `frame-ancestors 'self'`. نیاز به `worker-src blob:` برای Three.js در صورت استفاده بررسی شود.
- ابتدا `Content-Security-Policy-Report-Only`، پس از رفع تخلف‌ها حالت اجرایی.
- کوکی‌ها: `Secure`, `HttpOnly`, `SameSite=Lax`.

## 8. Installer و Updater وب

- فعال فقط در صورت وجود توکن در `.env` (و فایل قفل وجود نداشته باشد)؛ پس از نصب موفق فایل قفل ایجاد و مسیر 404 می‌دهد.
- Updater فقط برای نقش Admin و با توکن/تأیید مجدد رمز؛ هر اجرا در Audit و لاگ.
- بدون نمایش جزئیات خطا یا Secret در خروجی.
- Rate Limit، CSRF، و (اختیاری) محدودسازی IP.
- پس از استفاده: توصیه حذف/غیرفعال کردن مسیر؛ در چک‌لیست استقرار اجباری.

## 9. Secrets و محیط

- `.env` خارج از Document Root؛ مجوز فایل محدود (حداقل غیرقابل‌خواندن برای وب، مثلاً 640 یا 600 بسته به هاست).
- `APP_DEBUG=false`، `APP_ENV=production`، `APP_KEY` تصادفی و یکتا برای Production.
- کلیدهای API (ملی‌پیامک، SMTP، GitHub) فقط در `.env`؛ هرگز در Git یا لاگ.
- جداسازی Secret ها بین Staging و Production.
- چرخش کلید پس از افشا یا تغییر تیم.

## 10. حریم خصوصی و داده‌ها

- کمینه‌سازی: فقط داده لازم جمع‌آوری شود.
- IP و User-Agent: به‌صورت Hash با نمک یا کوتاه‌شده برای ضد اسپم؛ نگهداری محدود.
- Retention پیشنهادی (نیازمند تأیید مالک): درخواست‌های بسته‌شده/اسپم پس از مدت مشخص حذف یا ناشناس شوند.
- صفحه حریم خصوصی واقعی و متناسب با داده‌های جمع‌آوری‌شده (متن توسط مالک تأیید شود).
- لاگ‌ها و Audit بدون رمز، توکن، متن کامل پیام مشتری.
- Backup رمزنگاری/محافظت‌شده و خارج از وب.
- دسترسی مدیر به PII با نقش و ثبت Audit.

## 11. فایل‌ها و Document Root

- فقط `public/` (یا معادل آن در ساختار جایگزین) در معرض وب است.
- `.htaccess` برای رد دسترسی به `.env`, `.git`, `composer.*`, `*.log`, `storage`, `vendor` در ساختارهای جایگزین.
- لیست دایرکتوری (`Options -Indexes`) خاموش.
- مجوزها: فایل‌ها 644، پوشه‌ها 755، `storage` و `bootstrap/cache` قابل نوشتن برای کاربر PHP (طبق هاست)، بدون 777.
- حذف فایل‌های تشخیص (`probe.php` و مشابه) پس از استفاده.

## 12. وابستگی‌ها و زنجیره تأمین

- `composer audit` و `npm audit` پیش از هر Release؛ بررسی مجوز و نگهداری.
- قفل نسخه (`composer.lock`, `package-lock.json`) Commit شود.
- بدون اسکریپت Postinstall ناشناخته؛ بدون CDN.
- بروزرسانی امنیتی دوره‌ای (حداقل ماهانه) و پس از هر هشدار مهم.

## 13. خطا و مانیتورینگ

- نمایش صفحه خطای عمومی؛ جزئیات فقط در لاگ.
- لاگ `daily` با نگهداری محدود؛ اعلان ایمیلی برای خطاهای بحرانی با Throttle.
- صفحه 404 واقعی با Status Code درست؛ 403/419/429/500 سفارشی و بدون افشا.
- Audit Log برای: ورود/خروج/ورود ناموفق، تغییر رمز/نقش/مجوز، انتشار/حذف محتوا، تغییر تنظیمات، اجرای Installer/Updater، دسترسی به PII.

## 15. پاسخ به رخداد (خلاصه)

1. شناسایی و ثبت زمان/دامنه.
2. مهار: غیرفعال‌سازی حساب/کلید مشکوک، فعال‌سازی حالت تعمیر در صورت نیاز.
3. چرخش Secret ها و رمزها، ابطال نشست‌ها.
4. بررسی Audit و لاگ‌ها؛ تعیین داده‌های درگیر.
5. بازیابی از Backup در صورت لزوم.
6. ثبت در `debug_log.md` و افزودن تست/کنترل برای جلوگیری از تکرار.
7. اطلاع‌رسانی به افراد متأثر در صورت نشت داده شخصی.
